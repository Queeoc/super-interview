# Phase 9 前端开发的路径图

## 1. 文档目标

本文档用于规划 `super-interview` 的 Phase 9 前端建设方案。当前阶段只建立独立前端项目的实施蓝图，不生成任何前端业务代码，不替换现有 `static/` 页面，也不改动后端 API。

本阶段的目标是：

- 保留现有 `static/` 作为旧版/过渡入口
- 新增 `frontend/` 作为独立 React 前端项目规划区
- 明确新前端的一期功能边界、页面结构、技术选型与 API 对接方式
- 为后续工程化搭建与页面开发提供可直接执行的路径图

## 2. 项目目标

新前端将作为 `super-interview` 的主要展示层，面向后续正式前后端分离开发。它承担用户主流程体验，包括：

- 文字面试
- 简历上传与查看
- Skill 选择与查看
- 知识库上传与检索验证

保留现有 `static/` 的原因：

- 兼容已有访问入口
- 作为联调期过渡页面
- 在新前端未完成前保留兜底和回退路径

本阶段明确只覆盖以下能力：

- 文字面试主流程
- 简历上传、列表、详情预览
- Skill 列表与详情查看
- 知识库上传与检索验证

本阶段不纳入：

- Provider 管理
- AIOps 页面迁移
- React 前端代码实现
- `static/` 页面替换

## 3. 技术方案

新前端采用前后端分离方案，默认本地开发形态为：

- `frontend` 本地开发服务器
- FastAPI 后端 API 服务

技术栈固定如下：

- 核心框架：`React 18`
- 语言：`TypeScript`
- 构建工具：`Vite`
- 路由：`React Router`
- 服务端状态管理：`TanStack Query`
- 本地 UI 状态：组件状态 + `useReducer`
- 请求层：统一 `fetch` 封装
- 样式方案：`CSS Modules + 全局 design tokens`

状态管理约束：

- 不引入 Zustand 作为一期前提
- 不引入重量级全局状态库
- 不再把面试流程状态建立在 `localStorage` 之上

流式能力方案：

- 统一使用 `fetch + ReadableStream`
- 不使用 `EventSource`

原因如下：

- 现有主要流式接口为 `POST`
- 例如：
  - `/api/interview/sessions/{session_id}/answers`
  - `/api/chat_stream`
  - `/api/aiops`

## 4. 目标目录树

本阶段只创建文档，不创建代码文件。后续前端项目推荐目录结构如下：

```text
frontend/
├── 前端开发的路径图.md
├── 编码规范.md
├── package.json
├── tsconfig.json
├── vite.config.ts
└── src/
    ├── app/
    ├── pages/
    ├── features/
    ├── components/
    ├── services/
    ├── hooks/
    ├── types/
    ├── styles/
    └── utils/
```

推荐职责划分：

- `app/`：应用级初始化、路由、全局 Provider、应用壳
- `pages/`：页面级编排，不直接写复杂业务逻辑
- `features/`：按业务域组织模块，如 `interview`、`resume`、`knowledge`
- `components/`：通用可复用 UI 组件
- `services/`：API 客户端、SSE 解析、请求封装
- `hooks/`：通用 hooks 与领域 hooks
- `types/`：对齐后端 DTO 的前端类型
- `styles/`：全局 token、重置样式、布局基础样式
- `utils/`：纯工具函数

## 5. 页面路径图

一期页面路径规划如下：

- `/`
  - 首页/工作台
  - 展示主功能入口
  - 展示最近操作或最近会话入口

- `/interview`
  - 面试配置页
  - 选择 Skill
  - 选择简历
  - 创建面试会话

- `/interview/:sessionId`
  - 面试对话页
  - 展示当前题目
  - 录入答案
  - 展示 SSE 推进过程
  - 提供报告查看入口

- `/resume`
  - 简历中心
  - 上传简历
  - 查看简历列表
  - 查看简历详情预览

- `/knowledge`
  - 知识库工作台
  - 上传知识库文档
  - 发起检索验证
  - 展示命中结果

- `/skills`
  - Skill 列表页
  - Skill 详情查看
  - 可查看 reference section

预留但不进入 v1：

- `/providers`
  - 仅保留扩展位
  - 当前不纳入页面实现规划

## 6. 功能模块与后端 API 对应

当前后端已具备的一期核心 API 如下。

### 6.1 Skill 模块

- `GET /api/skills`
- `GET /api/skills/{skill_id}`
- `GET /api/skills/{skill_id}/reference-section`

页面使用方式：

- `/skills` 展示 Skill 列表
- `/interview` 创建面试时拉取 Skill 选项
- Skill 详情页展示描述、分类、参考资料摘要

### 6.2 简历模块

- `POST /api/resumes/upload`
- `GET /api/resumes`
- `GET /api/resumes/{resume_id}`

页面使用方式：

- `/resume` 上传简历并查看列表
- `/interview` 选择已上传简历发起面试
- `/resume` 查看单份简历详情与解析结果

### 6.3 面试模块

- `POST /api/interview/sessions`
- `GET /api/interview/sessions/{session_id}`
- `POST /api/interview/sessions/{session_id}/answers/draft`
- `POST /api/interview/sessions/{session_id}/answers`
- `POST /api/interview/sessions/{session_id}/complete`
- `GET /api/interview/sessions/{session_id}/report`
- `GET /api/interview/sessions/{session_id}/report/export`

页面使用方式：

- `/interview` 创建会话
- `/interview/:sessionId` 获取当前会话快照
- `/interview/:sessionId` 提交答案并消费 SSE 事件
- `/interview/:sessionId` 手动结束会话
- `/interview/:sessionId` 拉取报告与导出信息

### 6.4 知识库模块

- `POST /api/knowledge/upload`
- `POST /api/knowledge/search`

页面使用方式：

- `/knowledge` 上传文档后即时验证检索结果
- 页面只做“上传 + 检索工作台”，不做完整后台管理

### 6.5 健康检查

- `GET /api/health`

页面使用方式：

- 可作为应用启动后的连接检查
- 可用于开发环境排查后端状态

## 7. 数据流与关键约束

### 7.1 访客态与凭证

前端所有请求默认使用：

```ts
credentials: 'include'
```

原因：

- 后端当前通过 `visitor_id` Cookie 维护匿名访客态
- 简历、面试、知识库等功能都依赖该访客标识进行数据隔离

因此文档必须记录以下事实：

- `visitor_id` 是当前前后端协作的关键上下文
- 前端请求不能省略 Cookie 凭证
- 面试、简历、知识库的一致性以同一访客 Cookie 为前提

### 7.2 CORS 约束

当前后端 CORS 配置为：

- `allow_origins=["*"]`
- `allow_credentials=True`

真正进入前后端分离联调前，必须补齐后端配置调整：

- 不能继续使用通配源
- 需要改为显式前端源列表
- 否则 Cookie 跨域不会稳定可用

这是 Phase 9 真正落地前的已知前置约束，必须在前端文档中明确记录。

### 7.3 知识库能力边界

当前知识库 API 只支持：

- 文档上传
- 检索查询

当前尚不具备：

- 知识库列表
- 知识库详情
- 知识库删除
- 完整知识库后台管理

因此 `/knowledge` 在 v1 中定位为：

- 上传与检索验证工作台

而不是：

- 完整后台管理页

### 7.4 面试状态源

面试主流程的事实源应固定为：

- 服务端会话快照
- SSE 事件流

明确禁止沿用旧 `static/` 中“本地缓存即事实源”的做法。

前端状态同步原则：

- 会话初始数据来自 `GET /api/interview/sessions/{session_id}`
- 提交答案后，增量体验来自 SSE
- `done` 后应刷新一次会话快照或报告
- `localStorage` 不得作为面试历史的唯一事实源

## 8. SSE 事件适配说明

面试流式接口使用：

- `POST /api/interview/sessions/{session_id}/answers`

当前后端事件类型为：

- `status`
- `plan`
- `content`
- `report`
- `step_complete`
- `done`
- `error`

前端必须统一实现事件分发器，禁止在页面层手写字符串判断并散落处理逻辑。

推荐 UI 映射如下：

- `status`
  - 展示当前流程状态提示
  - 如“正在评估答案”“正在规划下一步”

- `plan`
  - 展示阶段计划区块
  - 适合用于说明系统接下来将执行的步骤

- `content`
  - 作为流式正文增量写入
  - 用于更新当前 AI 输出内容

- `step_complete`
  - 展示阶段完成提示
  - 用于强化用户对流程推进的感知

- `report`
  - 展示报告预览区块
  - 可作为最终评估报告的提前展示

- `done`
  - 结束当前流式消费
  - 立即刷新一次会话快照或报告

- `error`
  - 展示错误提示
  - 保留重试入口

补充说明：

- `chat_stream` 与 `aiops` 也采用类似的 POST 流式消费方式
- 但这两个接口不进入新前端一期主范围
- 一期流式抽象仍应兼容未来复用到其他流式接口

## 9. 页面级实施顺序

建议按以下子阶段推进：

### Phase 9.1：搭建前端工程基座

- 初始化 `React + TypeScript + Vite`
- 建立路由、QueryClient、全局样式 token
- 建立 `apiClient` 与流式消费基础设施

### Phase 9.2：Skill / 简历 / 面试主流程接入

- 完成 Skill 列表与详情
- 完成简历上传、列表、详情
- 完成面试创建、会话页、SSE 推进、报告查看

### Phase 9.3：知识库工作台接入

- 完成知识库文档上传
- 完成知识检索表单
- 完成检索结果展示

### Phase 9.4：联调、错误态与样式统一

- 补齐 loading / empty / error 状态
- 调整桌面端与移动端布局
- 核对跨域、Cookie、会话一致性问题

### Phase 9.5：保留 `static/` 并补充切换说明

- 保持旧入口可用
- 明确新旧前端并存关系
- 为后续切换正式入口准备说明文档

## 10. 与现有 `static/` 的共存策略

当前仓库中的 `static/` 仍继续保留，定位如下：

- 旧版入口
- 过渡页面
- 联调回退方案

新前端在保留期内的策略：

- 不覆盖 `/` 根入口
- 不直接替换现有静态文件
- 本地开发阶段通过独立 dev server 接入
- 后续部署阶段可通过独立路径或独立域名接入

推荐演进顺序：

1. 保留 `static/`
2. 独立开发 `frontend`
3. 联调验证后再决定是否迁移默认入口
